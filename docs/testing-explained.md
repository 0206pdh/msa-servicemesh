# 이 프로젝트는 무엇을, 왜 이렇게 테스트했는가

이 문서는 사전 지식이 전혀 없는 사람도 처음부터 끝까지 읽으면 "이 프로젝트가 정확히 무엇을 알아내려
했고, 왜 하필 이런 방식으로 테스트했으며, 실제로 무엇을 확인했는지"를 이해할 수 있도록 쓴 설명서다.
결과 수치 자체는 [PORTFOLIO.md](../PORTFOLIO.md)에 정리되어 있고, 이 문서는 그 수치가 **어떤 질문에
답하기 위한 것이고 왜 그런 실험 설계를 골랐는지**에 집중한다.

---

## 0. 이 프로젝트가 구하려는 것

### 0.1 실무적 배경

여러 개의 작은 서비스로 나뉜 시스템(MSA, Microservices Architecture)에서는 서비스끼리 네트워크로
통신한다. 이 통신에 "Service Mesh"라는 인프라 계층을 끼워 넣으면 서비스 코드를 거의 바꾸지 않고도
암호화, 접근 제어, 재시도, 상세한 관측(누가 누구를 얼마나 자주, 얼마나 느리게 호출했는지)을 얻을 수
있다. 하지만 이 인프라 계층은 공짜가 아니다 — 모든 요청이 추가 프로세스(proxy)를 거치게 되므로 CPU,
메모리, 네트워크 대역폭, 그리고 응답 시간이 늘어날 수 있다.

실무에서 자주 나오는 질문은 이거다: **"Service Mesh를 도입하면 얼마나 느려지고, 얼마나 더 많은 자원을
쓰게 되는가? 그리고 그 대가로 얻는 기능이 그만한 가치가 있는가?"** 이 질문에 "일반적으로는~" 같은
모호한 답 대신, 실제로 같은 시스템을 여러 구성으로 반복 측정해서 숫자로 답하는 것이 이 프로젝트의
목적이다.

### 0.2 핵심 질문 (하나로 요약)

> No Mesh(Mesh 없음), Istio Sidecar, Istio Ambient, Ambient + Waypoint 네 가지 구성은 같은 워크로드에서
> 성능·자원·관측성·회복탄력성에 어떤 차이를 만드는가? 그리고 발견된 병목은 어떤 변경으로 개선할 수
> 있는가?

### 0.3 답을 구하는 방식 (한 문장 요약)

**"같은 애플리케이션, 같은 부하를, Mesh 구성만 바꿔가며 여러 번 반복 실행하고, 그 차이가 우연이 아니라
통계적으로 믿을 만한 차이인지까지 확인한 뒤에만 결론으로 인정한다."** 한 번 측정해서 나온 숫자 하나를
믿지 않고, 왜 10~15번씩 반복하는지, 왜 통계적 신뢰구간을 계산하는지는 아래 2장에서 자세히 설명한다.

---

## 1. 알아야 할 기본 개념

### 1.1 MSA (Microservices Architecture)

큰 애플리케이션을 하나의 프로그램으로 만드는 대신, 독립적으로 배포·확장할 수 있는 작은 서비스 여러 개로
나누는 구조다. 배포는 유연해지지만, 원래 프로그램 내부의 "함수 호출"이었던 것이 이제는 "네트워크 호출"이
된다. 네트워크 호출은 함수 호출과 달리 실패할 수 있고(타임아웃, 연결 끊김), 느려질 수 있고, 도청/변조당할
수 있다 — 이 문제들을 다루는 인프라가 바로 Service Mesh다.

### 1.2 Service Mesh란 무엇인가

애플리케이션 코드를 거의 건드리지 않고 서비스 간 통신에 아래 기능을 얹어주는 인프라 계층이다.

- **서비스 신원 확인과 mTLS(상호 인증 암호화)** — "이 요청이 진짜 서비스 B에서 온 게 맞는지" 확인하고
  통신 내용을 암호화한다.
- **트래픽 라우팅** — 어떤 버전의 서비스로 요청을 보낼지 세밀하게 제어한다.
- **타임아웃/재시도/circuit breaker** — 장애가 난 서비스에 계속 요청을 보내지 않도록 자동으로 막는다.
- **요청 단위 지표·로그·추적(trace)** — 어떤 요청이 어느 서비스를 거쳐서 얼마나 걸렸는지 자동으로
  기록한다.

이 기능들은 보통 "프록시(proxy)"라는 작은 중계 프로그램이 실제 요청을 가로채서 처리하는 방식으로
구현된다. **이 프록시가 요청 경로에 끼어드는 것 자체가 이 프로젝트가 측정하려는 "비용"의 근원이다.**

### 1.3 이 프로젝트가 비교하는 네 가지 구성

```text
No Mesh:            Client → 서비스 A → 서비스 B                (프록시 없음)

Sidecar:            Client → [A + 전용 프록시] → [전용 프록시 + B]   (Pod마다 프록시 1개씩)

Ambient:             Client → [A] → 노드 공유 프록시(ztunnel) → 노드 공유 프록시 → [B]

Ambient + Waypoint:  Client → [A] → ztunnel → Waypoint(선택 경로만) → ztunnel → [B]
```

- **No Mesh**: Service Mesh를 아예 쓰지 않는 기준선(baseline)이다. 다른 세 구성의 "비용"을 계산하려면
  비교 기준이 있어야 하므로 반드시 먼저 측정한다.
- **Sidecar**: 요청을 처리하는 애플리케이션 Pod마다 전용 프록시(Envoy)를 하나씩 같이 띄우는 전통적인
  방식이다. Pod 수만큼 프록시가 늘어나므로, Pod가 많아지면 프록시 자원 총량도 그만큼 늘어난다는 것이
  이 방식의 특징이다.
- **Ambient**: Pod마다 프록시를 넣는 대신, Kubernetes 노드(서버)마다 하나씩 있는 공유 프록시("ztunnel")가
  그 노드 위의 여러 Pod의 트래픽을 대신 처리한다. 이론적으로는 Pod 수가 늘어도 노드당 프록시 개수는
  그대로이므로 자원이 덜 늘어난다 — 이게 사실인지를 이 프로젝트에서 직접 확인했다(6장 참고).
- **Ambient + Waypoint**: Ambient의 기본 프록시(ztunnel)는 암호화와 기본 연결 관리(L4, 4번 참고)만
  담당한다. HTTP 경로 기반 라우팅이나 상세 HTTP 로그 같은 고급 기능(L7)이 필요한 서비스에만 선택적으로
  "Waypoint"라는 추가 프록시를 하나 더 배치할 수 있다.

### 1.4 L4와 L7

- **L4 (Transport Layer)**: TCP 연결, IP, 포트 정도만 보고 트래픽을 처리하는 수준. "누가 누구에게
  접속했는지"는 알지만 "무엇을 요청했는지"는 모른다.
- **L7 (Application Layer)**: HTTP 메서드, 경로(path), 헤더까지 들여다보고 처리하는 수준. "이 요청이
  `GET /api/v1/orders`였다"는 것까지 안다.

L7은 더 세밀한 제어와 관측을 제공하지만, 요청 내용을 실제로 해석해야 하므로 처리 비용이 더 크다. Ambient
의 기본 프록시(ztunnel)는 L4까지만 처리하고, L7이 필요한 곳에만 Waypoint를 추가하는 것이 Ambient
아키텍처의 핵심 설계 철학이다.

### 1.5 mTLS (Mutual TLS)

일반 TLS(https)는 클라이언트가 서버의 신원만 확인한다. mTLS는 **양쪽 다** 서로의 인증서를 확인하고
통신을 암호화한다 — "서버가 진짜 서버인지"뿐 아니라 "요청을 보낸 게 진짜 등록된 서비스인지"까지
검증한다. Service Mesh가 제공하는 대표적인 보안 기능이며, 이 프로젝트에서는 mTLS 자체가 성능 비용의
얼마나 큰 부분을 차지하는지를 실제로 껐다 켜보며 측정했다(6.8절).

### 1.6 성능을 나타내는 숫자들

- **지연시간(latency) 백분위수 p50/p95/p99**: 전체 요청을 빠른 순서로 줄 세웠을 때, p50은 딱 중간
  (절반이 이보다 빠름), p95는 95%가 이 시간 안에 끝남(가장 느린 5%는 제외), p99는 99%가 이 시간 안에
  끝남(가장 느린 1%만 제외)을 뜻한다. **평균만 보면 안 되는 이유**: 예를 들어 999개 요청이 10ms, 1개
  요청이 10,000ms 걸렸다면 평균은 20ms 정도로 괜찮아 보이지만, 그 "1개"가 실제 사용자에게는 심각한 지연
  경험이다. p99는 이런 "가끔 아주 느린 요청"을 놓치지 않으려고 본다.
- **처리량(throughput)과 RPS**: 초당 몇 개의 요청을 처리했는지(Requests Per Second). "목표 RPS"는
  발생시키려던 부하, "달성 RPS"는 실제로 처리된 부하다. 둘이 크게 다르면 시스템이 목표 부하를 감당하지
  못했다는 뜻이다.
- **오류율(error rate)**: 전체 요청 중 실패한 비율.
- **CPU-초(core-seconds)**: CPU를 1개 코어 기준으로 1초 동안 100% 사용한 양을 "1 core-second"라고 한다.
  프록시가 요청을 처리하는 데 CPU를 얼마나 썼는지를 이 단위로 측정한다.

## 2. 측정 방법론: 왜 이렇게 설계했는가

### 2.1 왜 한 번만 측정하지 않고 10~15번 반복하는가

서버 성능 측정은 항상 약간씩 흔들린다 — 같은 조건에서 같은 테스트를 두 번 돌려도 정확히 같은 숫자가
나오지 않는다(다른 프로세스의 순간적인 부하, OS 스케줄링, 네트워크 지연의 미세한 변동 등). 한 번의
측정값만 보고 "Sidecar가 Ambient보다 느리다"고 말하면, 그 차이가 진짜 구성 차이 때문인지 아니면 그날의
우연한 변동 때문인지 구분할 수 없다. 그래서 같은 조건을 **10~15번 독립적으로 반복 측정**하고, 그 값들의
분포를 본다.

### 2.2 왜 10~15번인가 (Bootstrap 신뢰구간과 정밀도 게이트)

반복한 값들이 흩어져 있는 정도(불확실성)를 숫자로 나타낸 것이 **신뢰구간(Confidence Interval, CI)**
이다. "95% 신뢰구간이 [30ms, 34ms]다"는 대략 "진짜 값이 30~34ms 사이에 있을 가능성이 높다"는 뜻이다.
이 프로젝트는 신뢰구간을 계산할 때 **bootstrap**이라는 방법을 쓴다 — 실제로 측정한 값들(예: 12개의 p99
값)에서 복원추출로 10,000번 다시 뽑아서 그때마다의 중앙값을 계산하고, 그 10,000개 중앙값들이 흩어진
범위를 신뢰구간으로 삼는다. 이 방법은 데이터가 정규분포를 따른다고 가정하지 않아도 되므로, 서버 latency
처럼 한쪽으로 치우친(가끔 아주 느린 값이 섞이는) 데이터에 더 적합하다.

측정은 최소 10회부터 시작해서, 신뢰구간의 폭이 미리 정한 기준(정밀도 게이트)보다 좁아지면 그 시점에
멈춘다(`STOP_PRECISION_REACHED`). 15회까지 반복해도 기준을 못 채우면 "이 조건에서는 이 정도 반복으로는
더 좁혀지지 않는다"는 뜻으로 `INCONCLUSIVE_MAX_RUNS`라고 명시적으로 기록하고 멈춘다 — 무한정 반복하지
않는다.

**왜 상대 기준과 절대 기준을 같이 쓰는가(ADR-0023)**: 처음에는 "신뢰구간 폭이 중앙값의 5% 이내"처럼
상대적 기준만 썼다. 그런데 이 클러스터의 latency 자체가 워낙 작다 보니(25~40ms 수준) 5%는 1~2ms밖에 안
되는 매우 엄격한 기준이 되어 버려서, 15번을 반복해도 절대 수렴하지 않았다. 그래서 "상대 5% **또는**
절대 5ms 중 하나만 만족하면 통과"로 기준을 완화했다 — 작은 절대값의 지표에서 상대 기준이 비현실적으로
엄격해지는 문제를 해결한 것이다.

### 2.3 왜 "설정 지문(config fingerprint)"으로 결과를 관리하는가

실험 도중에 코드나 설정을 고치는 일이 실제로 있었다(예: 정밀도 게이트 공식을 바꾸는 등). 그런데 이미
측정해 둔 데이터가 "옛날 설정으로 측정한 것"인지 "지금 설정으로 측정한 것"인지 구분하지 못하면, 서로
다른 조건에서 나온 값을 하나의 통계로 섞어버리는 심각한 오류가 생긴다. 그래서 실험 설정 전체(부하 조건,
워크로드 정의, 반복 횟수 기준 등)를 하나의 문자열로 합친 뒤 SHA-256 해시값을 계산해 "이 run이 정확히
어떤 설정으로 측정됐는지"를 지문처럼 기록한다. 지문이 다른 run은 통계에 섞지 않고 자동으로
제외(`SUPERSEDED_CONFIG_FINGERPRINT`)한다.

### 2.4 왜 무효(invalid) run을 지우지 않고 남겨두는가

측정 중 실패(예: Kubernetes 노드 재부팅, 부하 발생기 자체의 병목, 시간 동기화 오류)가 섞여 들어올 수
있다. 이런 run은 통계 계산에서는 제외하지만, **삭제하지 않고 왜 무효인지 이유와 함께 그대로
보존한다.** 나중에 "왜 이 조건은 다른 조건보다 반복 횟수가 많았지?"를 추적할 수 있어야 하고, 실패를
숨기지 않는 것이 이 프로젝트의 신뢰성 원칙이기 때문이다.

### 2.5 profile 간 비교는 왜 "독립 2-표본" 방식인가 (엄밀히는 "짝지어진 비교"가 아님)

No-Mesh, Sidecar, Ambient는 각각 완전히 별도의 반복측정 세션으로 측정됐다(예: Sidecar의 3번째 반복과
Ambient의 3번째 반복은 서로 관련이 없다 — 다른 시각에, 다른 반복 횟수로 측정됐다). 이런 경우 통계적으로
정확한 방법은 "각 그룹에서 각각 독립적으로 다시 뽑아보는(resample)" **독립 2-표본 bootstrap**이다 — A
그룹에서 10,000번, B 그룹에서 따로 10,000번 다시 뽑아서 "B의 중앙값 − A의 중앙값"이 매번 얼마나
나오는지를 보고, 이 차이값들의 95% 범위가 0을 포함하지 않으면 "통계적으로 유의한 차이"로 인정한다. 이
방법은 같은 실행 번호끼리 짝지어서 비교하는 것("paired")과는 다르다 — 애초에 짝지을 방법이 없는 독립된
두 실험 세션을 비교하는 것이므로, 이 차이를 문서에 명확히 구분해서 적어 놓았다.

### 2.6 "통계적으로 유의함"과 "실질적으로 중요함"은 다르다

이 프로젝트에서 계속 강조하는 것 중 하나다. 예를 들어 Phase 8에서 "목표 RPS 차이가 통계적으로 유의하다"는
결과가 나온 적이 있는데, 그 차이는 0.0003 RPS(초당 0.0003번)였다 — 통계적으로는 "우연이 아니다"라고
말할 수 있어도 실무적으로는 아무 의미가 없는 크기다. 그래서 이 프로젝트는 모든 유의한 결과에 대해
**"크기가 실제로 의미 있는가"**를 항상 같이 판단해서 적었다.

### 2.7 여러 번 검정하면 우연히 유의한 결과가 나올 수 있다 (다중비교 문제)

동전을 100번 던져서 "앞면이 연속 5번 나왔다"는 결과 하나만 떼어놓고 보면 신기해 보이지만, 100번 던지는
동안 어딘가에서 그런 우연이 한 번쯤 나오는 것은 이상하지 않다. 이 프로젝트에서도 한 번의 비교 라운드에서
수십 개의 지표를 동시에 검정했기 때문에(Phase 8에서 36개), 그중 1~2개는 순전히 우연으로 "유의하다"고
나올 수 있다는 걸 항상 염두에 두고, 다음 조건에서도 같은 방향으로 재현되는지를 추가로 확인한 뒤에만
확정된 결론으로 인정했다.

## 3. 실제로 무엇을 테스트했는가 (Phase별)

### 3.1 사전 작업 — 용량 발견(Capacity Discovery)

**무엇을 했나**: 본격적인 비교에 앞서, 이 클러스터가 감당할 수 있는 최대 처리량("usable capacity",
`C*`)이 얼마인지부터 찾았다. 목표 RPS를 점점 2배씩 늘려가며(10 → 20 → 40 RPS...) 실패하는 지점을 찾고,
그 사이를 이분 탐색으로 좁혀서 "이 이상은 시스템이 감당 못 한다"는 경계값을 확인했다.

**왜 이걸 먼저 했나**: 부하 조건을 "그냥 적당히 100 RPS로 하자"처럼 임의로 정하면, 그 값이 시스템
용량의 몇 %인지도 모른 채 측정하게 된다. 예를 들어 시스템 용량이 30 RPS인데 100 RPS로 측정하면 그냥
전부 실패하는, 의미 없는 측정이 된다. 반대로 용량이 1000 RPS인데 8 RPS로만 측정하면 "여유로운 상태"만
보고 "한계 근처에서의 차이"는 놓치게 된다. 그래서 실제 용량(`C*`=28 RPS)을 먼저 확인하고, 그 비율로
"낮음(10%)/보통(30%)/높음(60%)/한계 근접(80%)"이라는 4개의 부하 조건(3/8/17/22 RPS)을 정했다 — 이렇게
하면 "여유로울 때"부터 "한계에 가까울 때"까지 골고루 비교할 수 있다.

### 3.2 No-Mesh 기준선 (Phase 4)

**무엇을 했나**: Service Mesh를 전혀 쓰지 않는 상태에서, 3개 서비스를 순서대로 호출하는
시나리오(`SYNC_CHAIN`: gateway → A → B → C)를 nominal/high/near-saturation(8/17/22 RPS) 세 조건에서
각각 10~15회 정식 반복측정했다.

**왜 이걸 먼저 측정했나**: 다른 모든 구성의 "추가 비용"은 이 기준선 대비 차이로 계산된다. 기준선이
없으면 "Sidecar에서 p99가 37ms 나왔다"는 숫자 자체는 좋은지 나쁜지 판단할 근거가 없다.

### 3.3 Istio Sidecar 기준선 (Phase 5)

**무엇을 했나**: 같은 3개 서비스에 Envoy 프록시를 Pod마다 하나씩 주입(inject)하고, 같은 세 부하 조건에서
정식 반복측정했다. 프록시(사이드카) 자체의 CPU/메모리도 애플리케이션 자원과 분리해서 별도로 측정했다.

**설계 중 있었던 조정**: 처음에 mTLS를 "STRICT"(암호화 없는 통신을 아예 거부)로 설정했더니 관측
시스템(Prometheus)이 앱 상태를 못 읽어와 버렸다(같은 포트로 API와 지표 수집을 같이 하고 있었기 때문).
그래서 "PERMISSIVE"(암호화된 통신과 평문 통신을 둘 다 허용)로 정정했다 — 이건 이 클러스터의 실제 제약
때문에 내려진 실용적 결정이었고, 그대로 기록해 두었다.

### 3.4 Istio Ambient 기준선 (Phase 6)

**무엇을 했나**: Pod마다 프록시를 넣는 대신 노드 공유 프록시(ztunnel)를 쓰는 Ambient 방식을 설치하고,
같은 세 부하 조건에서 정식 반복측정했다.

**측정에서 특별히 신경 쓴 점**: ztunnel은 그 노드 위의 **모든** Pod의 트래픽을 같이 처리하는 공유
프로세스다. 그래서 "ztunnel이 쓴 CPU-초"를 "이 실험이 발생시킨 요청 수"로 나눠서 "요청 1개당 비용"으로
계산하면 안 된다 — 같은 노드의 다른 워크로드가 쓴 몫까지 이 실험 탓으로 돌리는 오류가 생기기 때문이다.
그래서 ztunnel 자원은 "요청당 비용"이 아니라 "클러스터 전체의 절대 총량"으로만 기록하고, 이 사실을
데이터에도 `"attribution": "cluster-wide-shared-not-per-request"`라는 필드로 명시해 두었다.

### 3.5 Ambient + Waypoint (Phase 7) — 시도했으나 막힌 실험

**무엇을 확인하려 했나**: Ambient의 기본 프록시(ztunnel)는 L4(암호화, 연결 관리)까지만 하고 L7(HTTP
라우팅 등)은 못 한다. 이 L7 기능이 필요한 서비스 하나에만 선택적으로 Waypoint 프록시를 추가로 배치해서,
"선택적으로만 L7 기능을 켜는" 이 구조가 실제로 잘 동작하는지, 그리고 통과하는 트래픽에 얼마나 비용이
붙는지 확인하려 했다.

**무엇이 막혔나**: gateway에서 Waypoint까지는 연결이 성공했지만, Waypoint에서 실제 서비스로 가는
마지막 구간이 항상 "TCP 연결은 성공하지만 HTTP 요청이 즉시 리셋되는" 방식으로 실패했다. 노드를 분리해도,
`istioctl`로 설정을 직접 들여다봐도 원인을 찾지 못했고, Istio 버전을 완전히 바꿔서(1.30.3 → 1.29.6)
재설치해도 똑같이 재현됐다. **서로 다른 두 버전에서 동일하게 실패한다는 것은 특정 버전의 버그가 아니라
이 클러스터의 네트워크 구성(Cilium)과 Ambient Waypoint 아키텍처 사이의 근본적인 비호환일 가능성이
크다는 뜻**이라, 원인 규명을 여기서 멈추고 "확인된 한계"로 기록한 뒤 나머지 비교를 진행했다. (성능
프로젝트에서 "안 되는 이유를 못 찾았다"도 하나의 정직한 결과다 — 억지로 우회하거나 숨기지 않았다.)

### 3.6 Replica 확장 방향성 연구 (ADR-0027)

**무엇을 확인하려 했나**: "Sidecar는 Pod마다 프록시가 늘어나니 Pod 수(replica)가 늘면 프록시 자원
총량도 같이 늘어날 것"이고 "Ambient는 노드당 프록시가 고정이니 Pod 수가 늘어도 자원이 거의 안 늘어날
것"이라는 가설을 세우고, 실제로 서비스 하나(orchestrator-service)의 replica를 1→2→4개로 늘려가며
확인했다.

**왜 "정식" 측정이 아니라 "방향성" 측정으로 설계했나**: 이미 Phase 4~7에서 상당한 시간을 반복측정에
썼기 때문에, replica 3개 지점 × 2개 profile을 전부 정식 10~15회로 측정하면 시간이 지나치게 커진다. 그래서
반복을 3회로 줄이고, "통계적으로 확정된 결론"이 아니라 "방향이 맞는지"만 빠르게 확인하는 것으로 범위를
의도적으로 좁혔다(이 축소 자체도 ADR-0027에 근거와 함께 문서화했다).

**무엇을 확인했나**: 메모리는 가설과 정확히 일치했다 — Sidecar 총 메모리는 120→173MiB로 늘었고
(replica마다 프록시가 새로 생기니까), Ambient의 ztunnel 메모리는 15.8→16.1MiB로 거의 그대로였다. 다만
예상 밖으로 **Ambient의 latency가 replica가 늘수록 뚜렷하게 나빠졌다**(p99 51→99.5ms, 거의 2배) — 이건
3회 반복 데이터라 "방향성 참고"로만 기록해두고, 나중에 정식으로 재확인하기로 했다(→ 3.9절).

### 3.7 Phase 8 — profile 간 정식 통계 비교

**무엇을 했나**: Phase 4~6에서 각각 따로 측정해 둔 No-Mesh/Sidecar/Ambient 데이터를 서로 비교하는 도구를
새로 만들었다. 세 부하 조건 × 세 profile 쌍(No-Mesh vs Sidecar, No-Mesh vs Ambient, Sidecar vs Ambient)
× 6개 지표 = 36개 비교를, 2.5절에서 설명한 "독립 2-표본 bootstrap"으로 전부 수행했다.

**핵심 발견**: 36개 비교 중 요청당 네트워크 바이트 비교 9개는 **전부** 유의했고, 방향과 크기가
일관됐다 — Sidecar는 세 부하 조건 모두에서 No-Mesh보다 약 49% 더 많은 바이트를 썼고, Ambient는 1~2%만
더 썼다. 반면 latency 비교(18개)는 단 1개만 유의했는데, 그마저 다음 부하 단계에서 반대 방향으로
뒤집혀서 "확정된 결론"으로 보지 않고 "추가 확인이 필요한 신호"로만 남겼다(2.7절의 다중비교 문제를 실제로
적용한 사례다). 애플리케이션 자체의 CPU 사용량은 9번 비교 전부 유의한 차이가 없었다 — 이건 "Mesh
비용이 애플리케이션 코드 실행 자체에는 전이되지 않는다"는 의미 있는 부정적 결과다.

**시간축 상관 분석을 시도했다가 겪은 일**: "왜 특정 시점에 이런 값이 나왔는지" 더 깊이 파보려고 과거
run의 Prometheus/Tempo/Loki 데이터를 다시 조회하려 했는데, 관측 시스템 자체가 24시간만 데이터를
보관하도록 설정되어 있어서 대부분 사라진 뒤였다. (다만 Loki 로그는 설정과 달리 실제로는 삭제 로직이
꺼져 있어서 예상보다 오래 남아 있었지만, 열어보니 애플리케이션이 요청 단위 로그를 남기지 않아서 어차피
분석에 쓸 내용은 없었다.) 이건 "측정 결과 자체"가 사라진 게 아니라 — 그건 매 실행 직후
`summary.json`으로 이미 로컬에 저장해 뒀으므로 안전했다 — "더 깊이 원인을 캐보려는 부가 조사"가 막힌
것이었다. 앞으로는 이런 일이 없도록 매 실행마다 실제 시계열 데이터도 함께 저장하도록 고쳤다.

### 3.8 Phase 9 실험 1 — Sidecar의 mTLS를 꺼보기 (ADR-0028)

**무엇을 확인하려 했나**: 3.7절에서 발견한 "Sidecar가 네트워크 바이트를 49%나 더 쓴다"는 결과를 보고
세운 첫 번째 가설은 "이 증가분의 주된 원인이 mTLS 암호화(1.5절)일 것"이라는 것이었다. 이 가설을
검증하는 가장 직접적인 방법은 **mTLS만 끄고 나머지는 전부 그대로 둔 채** 다시 측정해서 네트워크
바이트가 실제로 줄어드는지 보는 것이다 — "독립 변수 하나만 바꾼다"는 실험 설계의 기본 원칙(2.5절 참고)을
그대로 적용한 것이다.

**어떻게 검증했나**: `PeerAuthentication`이라는 Istio 설정으로 mTLS를 끈("DISABLE") 뒤, 같은 부하
조건(nominal, 8 RPS)에서 정식 10~15회 반복측정을 새로 했다. 실제로 mTLS가 꺼졌는지도 Envoy의 내부
설정을 직접 열어봐서(`istioctl proxy-config listener`) 암호화 관련 설정이 사라졌는지 확인한 뒤에
측정을 시작했다 — "설정 파일에 그렇게 썼다"와 "실제로 그렇게 동작한다"는 다른 문제이기 때문이다.

**결과 — 가설은 기각됐다**: mTLS를 꺼도 네트워크 바이트는 겨우 1%(341바이트)만 줄었다. 3.7절에서 찾은
전체 오버헤드(10,469바이트, 49%)의 3% 남짓만 mTLS 때문이라는 뜻이다. **나머지 97%는 암호화가 아니라
다른 원인(예: Envoy가 붙이는 HTTP/2 프레이밍, 프록시-프록시 사이 추가 홉 자체의 부가 정보)에서 온다** —
"그럴듯해 보이는 첫 번째 가설"이 실제로는 틀렸다는 것을 직접 측정으로 확인하고 그대로 기록한 사례다.

**측정 도중 발견한 방법론적 문제(정직하게 기록)**: 비교 대상으로 쓴 기존 Sidecar 데이터는 Istio
1.30.3에서 측정된 것이었는데, 이번 측정 시점에는 클러스터가 (Waypoint 재시도 과정에서) Istio 1.29.6으로
바뀌어 있었다 — 즉 "mTLS 모드 하나만 바꾼" 비교가 아니라 부지불식간에 "Istio 버전도 같이 다른" 비교가
되어버린 것이다. 같은 버전으로 다시 측정해서 이 오차 요인을 없애는 방안을 시작했지만, 몇 시간이 더
걸리는 것에 비해 버전 차이가 결론을 뒤집을 가능성은 낮다는 판단하에 버전 차이를 감수하고 그대로
보고하기로 했다 — **네트워크 바이트 결론(mTLS 기여분이 작다)은 이 오차에 크게 영향받지 않지만, 함께
관찰된 "mTLS를 끄니 오히려 느려졌다"는 latency 결과는 이 오차 때문에 "확정 아님"이라는 꼬리표를 붙여서
보고했다.**

### 3.9 Phase 9 실험 2 — Ambient replica 확장 latency 저하를 정식으로 재확인 (ADR-0029, 진행 중)

**무엇을 확인하려 했나**: 3.6절에서 3회 반복만으로 관찰했던 "Ambient는 replica가 늘수록 latency가
나빠진다"는 결과를, 이번에는 Phase 4~8과 같은 수준(10~15회, bootstrap 신뢰구간)으로 정식 확인하는
실험이다.

**어떻게 설계했나**: orchestrator-service의 replica 수(1개 vs 4개, 효과가 가장 뚜렷했던 양 극단만
사용)를 독립 변수로 두고, 기존 Phase 6 canonical 데이터(replica=1)를 "before"로 재사용하고, replica=4만
새로 정식 반복측정한다 — 여기도 3.8절과 같은 "시간 대비 실익을 따져서 일부는 재사용하고 일부만 새로
측정한다"는 원칙을 일관되게 적용했다.

**현재 상태**: 이 문서를 작성하는 시점에 측정이 진행 중이다. 결과는 [PORTFOLIO.md](../PORTFOLIO.md)와
[CURRENT.md](CURRENT.md)에 완료되는 대로 반영된다.

---

## 4. 결과를 읽을 때 꼭 기억해야 할 것

- **"가장 빠른 Mesh"를 고르는 프로젝트가 아니다.** 기능 범위가 다른 구성(예: L7 기능이 있는 Sidecar와
  없는 기본 Ambient)을 "누가 더 빠른가"로만 비교하면 잘못된 결론이 된다.
- **통계적으로 유의하지 않다 = 차이가 없다는 뜻이 아니다.** 이 클러스터와 이 정도 반복 횟수로는 아주
  작은 차이(예: p95 5ms 미만)를 구분해낼 능력 자체가 없다. "차이를 발견하지 못했다"와 "차이가 없다는
  것을 증명했다"는 다른 말이다.
- **한 번 유의했다고 확정 결론이 아니다.** 다음 조건에서도 같은 방향으로 재현되는지 반드시 확인한다
  (2.7절).
- **비교 대상 사이에 의도하지 않은 차이(confound)가 없는지 항상 의심한다.** 이 프로젝트에서도 Istio
  버전이 실험 도중 바뀐 것을 나중에야 발견한 적이 있다(3.8절) — 발견 즉시 숨기지 않고 그대로 기록했다.
- **실패하거나 기각된 가설도 결과다.** mTLS 가설 기각(3.8절), Waypoint 연결 실패(3.5절) 모두 "원하는
  결과가 안 나왔다고 결과 자체를 감추지 않는다"는 원칙에 따라 그대로 남겨져 있다.

## 5. 이 문서에서 쓴 용어 빠른 사전

| 용어 | 뜻 |
|---|---|
| MSA | 하나의 큰 프로그램을 여러 개의 독립된 서비스로 나눈 구조 |
| Service Mesh | 서비스 간 통신에 보안·라우팅·관측 기능을 더해주는 인프라 계층 |
| Sidecar | Pod(서비스 실행 단위)마다 전용 프록시를 하나씩 붙이는 Mesh 구현 방식 |
| Ambient | 노드마다 공유 프록시(ztunnel) 하나로 여러 Pod의 트래픽을 처리하는 방식 |
| ztunnel | Ambient 방식에서 노드마다 배치되는 공유 프록시, L4(암호화·연결관리)만 담당 |
| Waypoint | Ambient에서 L7 기능이 필요한 서비스에만 선택적으로 추가하는 프록시 |
| L4 / L7 | 네트워크 처리 수준. L4는 연결 단위, L7은 HTTP 내용까지 이해하는 수준 |
| mTLS | 통신 양쪽이 서로의 신원을 인증서로 확인하고 암호화하는 방식 |
| p50/p95/p99 | 요청을 빠른 순서로 줄 세웠을 때 50%/95%/99% 지점의 응답 시간 |
| RPS | 초당 요청 수(Requests Per Second), 처리량의 단위 |
| CPU core-second | CPU 1개 코어를 100% 기준으로 1초 사용한 양 |
| 신뢰구간(CI) | 반복 측정값들의 불확실성 범위를 나타내는 통계량 |
| Bootstrap | 측정값에서 복원추출로 여러 번 다시 뽑아 신뢰구간을 계산하는 통계 기법 |
| 정밀도 게이트 | 신뢰구간이 충분히 좁아질 때까지 반복하고, 아니면 명시적으로 멈추는 규칙 |
| Config fingerprint | 실험 설정 전체를 해시값으로 표현해 서로 다른 설정의 결과가 섞이지 않게 하는 장치 |
| 독립 2-표본 비교 | 서로 관련 없는 두 그룹을 각각 따로 리샘플링해서 차이를 검정하는 통계 방법 |
| 통계적 유의성 | 관측된 차이가 우연일 가능성이 낮다는 뜻(크기의 실질적 중요성과는 별개) |
| Confound(교란 변수) | 의도치 않게 같이 바뀌어서 결과 해석을 어렵게 만드는 변수(예: 버전 차이) |
| Invalid run | 측정 실패 등으로 통계에 쓸 수 없지만, 이유와 함께 그대로 보존하는 실행 기록 |
